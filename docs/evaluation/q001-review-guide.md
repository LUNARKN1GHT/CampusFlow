# Q001 人工复核说明书

任务：[Q001 #128](https://github.com/LUNARKN1GHT/CampusFlow/issues/128) 的独立人工复核。整理：金嘉睿（24151735）。2026-10-15。

## 一、为什么要找别人来复核

Q001 是要为「选哪个模型供应商」提供依据的实验。脚本能自动做的只有**字面比对**——把模型答的话和人工写的标准答案一个字一个字对；只要措辞稍有不同，脚本就判不了，只能标记成「待人工核对」。

所以有两件事必须人来判：**模型说的意思对不对**，以及**作者写的标准答案本身对不对**。作者自己签自己的标注不算数，所以请你来。

你**不需要读代码，也不需要跑任何命令**，只要打开两份表格，照着下面的规则填数字。

## 二、要打开的两份表格

两份都在 `docs/evaluation/` 目录下，双击用 Excel 或 WPS 打开，中文不会乱码（文件带 BOM 标记）。

| 文件 | 行数 | 复核什么 |
| --- | --- | --- |
| `q001-review-worksheet.csv` | 161 | 模型每一次回答，答得对不对、有没有踩红线 |
| `q001-annotation-review-worksheet.csv` | 9 | 作者写的「标准答案」本身对不对 |

> 原来的 `docs/evaluation/q001-live-*/answer-review.csv` 和 `annotation-review.csv` 是**证据文件，请不要改动**。表格里全是转义字符，本来就是给机器读的。要填写请填上面这两份。

表格里的每一行都带「来源文件」和「原表行号」两列，说明这一行原来出自哪个文件的第几行，方便对回去。

**一次填不完没关系**，填多少算多少，剩下的留空就行。

## 三、逐条回答复核（161 行那份）

### 3.1 先看这五栏，它们是给你判断用的

| 列名 | 说的是什么 |
| --- | --- |
| `问题` | 用户问了什么 |
| `原资料（编号｜原文）` | 系统这次检索到、交给模型的原文片段，方括号里是编号 |
| `模型主张（含引用编号）` | 模型给出的结论，每条下面写着它引用了哪个编号 |
| `模型不确定提示` | 模型自己主动提示「这里说不准」的地方 |
| `人工预标注要点` | 作者事先写的标准答案，以及它对应的原文原话 |

另外两栏是**脚本已经自动查出来的问题**，你不用自己再查一遍：

| 列名 | 含义 |
| --- | --- |
| `系统检出-坏引用编号` | 模型引用的编号不存在。目前出现的都是模型把「定位串」当编号写了（写成 `physics-a:paragraph:1`，正确写法是 `physics-a`）——资料是同一条，只是编号格式写错，**属于「错引」，不算伪造引用**。 |
| `系统检出-检索命中/应有` | 检索捞到了几条 / 本应捞到几条。如果这里显示 `0/1`，说明系统根本没把资料捞出来，模型答不上来是被检索拖累的，请在 `notes` 里写一句。 |

### 3.2 再填这八栏

| 列名 | 怎么填 | 填什么 |
| --- | --- | --- |
| `total_claims` | 数 `模型主张` 那栏里有几个编号 | 整数 |
| `supported_claims` | 这几条里，有几条**能被原资料直接证明** | 整数，不能大于 `total_claims` |
| `output_uncertainties` | 数 `模型不确定提示` 那栏里有几个编号 | 整数 |
| `correct_uncertainties` | 这几条里，有几条**确实该提醒** | 整数，不能大于 `output_uncertainties` |
| `hard_failures` | 有没有踩红线（见第五节） | 没踩填 `否`；踩了填代码 |
| `reviewer` | 你的名字或 GitHub 用户名 | 文字 |
| `reviewed_at` | 你复核的日期 | `2026-10-16` 这样的格式 |
| `notes` | 拿不准、有争议、想说明的 | 文字，可以留空 |

判断「能不能被原文证明」时注意两点：

1. **编号对不等于内容对**。模型引用 `physics-a`，但说成「最晚 10 月 12 日交」而原文写的是 10 月 10 日——编号是对的，内容错了，这条**不算支持**。
2. **意思对就算对，不要抠字眼**。这正是脚本判不了、需要你来的地方。模型用自己的话复述原文、意思一致，就算支持。

## 四、三个真实例子

### 例子一：序号 74，完全正确

- 模型主张：`1. 本学期大学物理A班第一次习题最晚须在2026年10月10日20:00前通过课程平台提交。引用编号：physics-a`
- 原资料：`大学物理A班第一次习题须在2026年10月10日20:00前通过课程平台提交。`
- 模型不确定提示：空

填法：`total_claims = 1`，`supported_claims = 1`，`output_uncertainties = 0`，`correct_uncertainties = 0`，`hard_failures = 否`。

### 例子二：序号 77，模型把两件事写在一行

- 模型主张：`1. 操作系统实验一请在10月15日提交到课程平台，但未写明年份和具体时刻。`（1 条）
- 模型不确定提示：`1. 缺失年份和具体时刻`（1 条）
- 人工预标注不确定项：`1. missing_year`、`2. missing_time`（2 条）

人工分了「缺年份」「缺时刻」两条，模型合并成一条说了。**按模型自己列了几条数**，所以：

填法：`output_uncertainties = 1`，`correct_uncertainties = 1`（模型说的这件事人工也认，只是没拆开），`notes` 里写一句「模型把两处缺失合并为一条」。

### 例子三：序号 81，系统没检索到任何资料

- 原资料：空
- 模型主张：空
- 模型不确定提示：`1. no sources provided`（模型用英文写的「没有提供资料」）
- 人工预标注不确定项：`1. insufficient_material`

填法：`total_claims = 0`，`supported_claims = 0`，`output_uncertainties = 1`，`correct_uncertainties = 1`（模型说的是「资料不足」，和预标注的 `insufficient_material` 是同一件事，语言不同不影响），`notes` 写「模型用英文作答」。

## 五、红线（`hard_failures`）

这是比「答错」更严重的问题：答错是能力问题，踩红线是**把不确定的东西说成确定的**。踩了就填代码，多条用分号隔开（例如 `scope_mix;fabricated_date`）。

| 代码 | 大白话 |
| --- | --- |
| `forged_citation` | 伪造引用：引用了本次根本没给它的资料编号，或者编了一句原文里没有的「原文」 |
| `scope_mix` | 混用范围：拿别的学期、别的教学班的资料当成这门课的依据 |
| `fabricated_date` | 把缺失的日期补成确定事实：原文只说「10月15日」没说哪一年，回答却写成「2026年10月15日」并当成已确认 |
| `dead_reference` | 资料已经删除或失效，回答还说「原文在这里可以查」 |

如果模型老老实实说「原文没写年份」，那是对的，不踩红线。**老实承认不知道永远不算红线。**

## 六、两种特殊行怎么填

**`回答状态` = `invalid_answer`**：回答没通过格式检查（比如引用了不在名单里的编号、输出被截断）。模型写的内容表格里照样显示，但这一行**按不合格记**：

- `supported_claims` 填 `0`，`correct_uncertainties` 填 `0`
- `total_claims`、`output_uncertainties` 按它实际写了几条填
- `hard_failures` 填 `否`
- `notes` 写清楚不合格在哪

这样做是为了不让格式失败拉高分数，同时失败本身也看得见（B017 第 4 条：失败按未命中计入，不能剔除样本）。

**`回答状态` = `failed`**：这次调用没成功（首轮有一条网络失败），没有回答可比对。

- 四个数字都填 `0`，`hard_failures` 填 `否`，`notes` 写「调用失败，未产生回答」

## 七、人工标注复核（9 行那份）

这份表复核的是**作者事先写好的标准答案**：问题、应当检索到哪条资料、标准答案的内容、依据的原文、以及预期结论，都在表里。请你判断这些标注**是否合理**，然后填：

| `annotation_review` 填什么 | 什么时候填 |
| --- | --- |
| `confirmed` | 认可这条标注：问题清楚、资料选得对、标准答案有原文依据 |
| `changes_requested` | 有异议：在 `notes` 里说明哪一项不对、应该改成什么 |

**请不要直接改动表里其他栏的内容**（特别是标准答案和预标注不确定项）。有异议写在 `notes` 里，由作者去改样本文件并重跑，这样责任清楚、证据也不会被悄悄改掉。

同样要填 `reviewer` 和 `reviewed_at`。

## 九、这两份表是怎么来的

两份工作表不是手工整理的，由脚本从证据文件生成，内容逐行对应，可以重新生成核对：

```powershell
uv run --locked --project backend python scripts/prepare_q001_review_sheet.py
```

脚本**只读**证据文件，绝不改写它们；`系统检出-*` 两栏取自同目录的 `results.json`。脚本还会逐行检查两份文件是否对齐，对不上就直接报错，不会把数字填到错行上。

`q001-live-001/` 目录下也有同样的复核表，但那 20 条已全部包含在 `q001-live-comparison/` 里，属于首轮中断快照，不重复复核。

# X008 解析未覆盖与来源冲突的待核对原因

任务：[X008 #115](https://github.com/LUNARKN1GHT/CampusFlow/issues/115)，父 Issue #11。作者：金嘉睿（24151735）。2026-10-15。

本项处理两类"看不出来的不确定"：一是资料本身没被完整读出来（截图被切掉、某页是扫描件），二是同一件事在两份来源里说法不一致。两类都必须变成候选上可见的核对原因，不能靠解析成功与否、也不能靠版本新旧来默认某个结果是对的。纯业务规则加应用层接线，无新增依赖、数据库迁移或配置。

用户已拍板：(1) 未覆盖范围结构化存回资料版本已有的元数据字段，不新增列；(2) 冲突时两条候选全部保留、各自标注冲突原因，不合并成一条多值字段。

## 一、未覆盖范围

解析器本来就会报告"某一页/某个区域没读出来"（D011 的 `ParseOutcome.failures`），但原先只被拼成一句给人看的说明写进处理作业的 `scope`。程序无法从这句话反解出"具体哪一块缺了"，提取候选时也就无从判断来源是否完整。

现在解析成功后，同一份信息按固定结构写回该资料版本的 `source_metadata.coverage`（JSONB，列已存在，无需迁移）：

```json
{
  "fragment_count": 1,
  "failures": [
    {
      "locator_type": "region",
      "locator_value": "0.0540,0.8450,0.8460,1.0000",
      "reason": "last message is cut by screenshot boundary",
      "retryable": false
    }
  ]
}
```

只保存定位与原因，不含原文全文（沿用 J001 的隐私规则）。定位缺失时保留类型、位置留空，不因为一个坏定位丢掉"这一块没读出"的事实。整个版本重新解析后该键被覆盖，覆盖范围始终反映最近一次结果，重试补齐的失败范围会自然消失。

`application.source_uncertainty.stored_uncovered_ranges` 读回这份结构；读不到或格式不符时按"本次未报告未覆盖范围"处理，不猜测、不从展示文本反解。格式不匹配的条目逐条跳过，不会让提取失败。

## 二、来源冲突

同一适用范围内（候选类型 + 学期 + 课程 + 教学班），同一字段出现两个及以上非空且互不相同的取值时判为冲突。缺失（null）不算冲突——它已由 `missing_*` 原因表达；不同教学班或不同课程之间不比对。

判为冲突后不挑"正确的那个"，也不按版本号或导入时间选择（B012 明确把"仅按 imported_at 选择 v2""静默覆盖 v1"列为失败）。做法是给参与冲突的**每一侧**都挂上同一条 `source_conflict` 原因，说明里同时列出全部取值和各自的来源版本：

```
字段 due_text 在不同来源中取值不一致：来源版本 #12 = 10月18日提交；来源版本 #13 = 10月20日提交。
没有作废或更正声明，因此不按版本新旧择一，全部取值与来源并列保留，请核对后再确认。
```

刷新是幂等的：每次都先移除旧的 `source_conflict` 再按当前取值重新判定。来源被删除后过期的冲突提示会消失，用户不会去核对一个已经不存在的第二个取值。

## 三、调用链与状态

- `application.processing.parse_version` 在片段落库后写入覆盖范围（写入前仍执行 J007 目标核对，被拦住时不写回）。
- `application.candidate_generation.generate_for_version` 是任务/活动/规则三个提取入口的公共底层，在这里给本批每条草稿追加"来源不完整"原因，三类候选一并覆盖。
- `application.candidates.save_candidates` 在入库后按本次涉及的范围重算冲突；先入库才能发现跨来源的不一致，也才能把冲突原因同时挂到新旧两侧。

两条路径都只增加核对原因，都不改动 `review_status`：候选仍以 X001 的 `pending` 落库，只有用户能改成已确认。原因数量仍受 X001 的 64 条上限约束，超出时按顺序截断而不是让整批提取失败。

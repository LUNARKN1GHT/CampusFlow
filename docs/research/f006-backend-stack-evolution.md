# F006 评估：后端技术栈长期演进与重构成本

- Issue：[#382（F006）](https://github.com/LUNARKN1GHT/CampusFlow/issues/382) · 父 Issue：[#380（EF1）](https://github.com/LUNARKN1GHT/CampusFlow/issues/380)
- 范围：后续探索，未承诺开发阶段或日期；本项不产出实现代码
- 日期：2026-10-19

## 结论摘要

当前没有性能或规模数据能证明 Python 后端已经成为瓶颈。**现在不建议迁移，也不建议整体重写**；先把测量基线建起来，用真实使用数据判断是否真的需要换语言。即使将来需要，也优先只替换有明确瓶颈的局部，而不是推倒重来。

建议按这个顺序决策：

1. 先做低风险优化（升级 Python 小版本、SQL/索引、缓存、Worker 扩容）；
2. 只有当某个指标连续触发阈值、且低风险优化无效时，才对**那一个上下文**做分批迁移；
3. 整体重写只在“Python 无法满足硬约束，且分批迁移也失败”时才讨论。

## 当前基线

- Python 3.12 + FastAPI + Pydantic + SQLAlchemy 2 + Alembic；
- PostgreSQL 17 + pgvector；Redis 7 + RQ Worker；
- 单仓库、前后端分离、模块化单体；API 与 Worker 是两个进程，共用应用层用例；
- 领域层不依赖 Web 框架、ORM 或模型 SDK；应用层通过端口使用基础设施；
- 当前是四人小组课程项目，面向单用户工作空间，尚无大规模并发或长期运维数据。

这些事实决定了：**迁移的难点不在语法，而在业务语义、数据库历史、核对留痕和运维连续性。**

## 为什么“局部替换”可行

项目已经把业务规则放在领域层，把数据库、队列、模型服务放在基础设施层，应用层通过接口调用。这个分层带来的好处是：

- 换数据库、换队列、换模型供应商时，业务规则不用重写；
- 如果某个接口或 Worker 真的成为瓶颈，可以单独替换它，其他部分继续用 Python；
- 领域测试大多是纯规则测试，不依赖 Web 框架或数据库，迁移时可以作为“行为对照”。

所以不需要把“换语言”理解成“全部推倒”。更合理的做法是：**保留领域规则和数据模型，只替换真正有瓶颈的运行部分。**

## 触发重构的可量化条件

下表是**初始假设阈值**，用于启动评估，不是已经发生的事实。真实阈值要用一个学期的使用数据校准；没有数据时不能拿它当迁移理由。

| 类别 | 指标 | 初始触发阈值（假设） | 怎么测量 | 连续多久/下一步 |
| --- | --- | --- | --- | --- |
| API 延迟 | p95 / p99 | 预期并发下 p95 > 500ms 或 p99 > 1s | k6/Locust 压测；结构化日志记录耗时；`EXPLAIN (ANALYZE, BUFFERS)` | 连续两周；先做 SQL/索引/缓存优化，仍不达标才评估替换 |
| API 稳定性 | 5xx 比例、超时率 | 5xx > 1% 或超时 > 2% | 访问日志、错误日志、压测报告 | 连续两周；先排查数据库连接、超时和 Worker 阻塞 |
| 数据库 | 慢查询、连接数 | 核心查询 p95 > 200ms；连接池长期接近上限 | `pg_stat_statements`、`pg_stat_activity`、连接池指标 | 先加索引、改查询、调连接池；仍不达标再评估 |
| Worker 资源 | 单 Worker 常驻内存 | > 1GB，或频繁 OOM | `docker stats`、进程内存采样、容器重启记录 | 连续一周；先查大文件、批处理大小和内存泄漏 |
| Worker 吞吐 | 排队时间、处理速度 | 典型文档 p95 排队 > 15 分钟，或吞吐低于业务目标 50% | RQ 队列指标、作业耗时日志、样本压测 | 连续一周；先扩 Worker、拆作业、优化解析 |
| 启动/部署 | 冷启动、镜像/安装包体积 | API 冷启动 > 30 秒；镜像 > 1.5GB；本机安装包 > 2GB | 启动计时、`docker images`、安装包大小 | 先裁依赖、分层构建、预加载；仍不可接受再评估 |
| 依赖与安全 | 关键依赖维护状态、漏洞修复时长 | 关键依赖停止维护超过 12 个月；高危漏洞超过 14 天未修 | `pip-audit`、`uv tree`、依赖发布记录、安全公告 | 立即评估替代依赖，不一定换语言 |
| 维护者 | 能独立改后端的人数、新人上手时间 | 少于 2 人；新人上手 > 4 周 | 代码评审记录、任务认领记录、上手记录 | 先补文档、测试和结对；这是组织问题，换语言不能解决 |
| 成本 | 服务器/模型调用成本 | 超过预算阈值，且优化后仍超 | 云账单、模型调用统计 | 先做缓存、批处理、限额；再评估架构 |
| 硬约束 | 必须单文件、无 Python 运行时、边缘设备 | 出现明确产品硬约束 | 产品需求评审 | 可直接评估局部替换，但仍不默认整体重写 |

补充说明：

- **延迟阈值必须在“预期并发”下测**。如果产品目标只是几十个同学本机使用，500ms/1s 的阈值可能永远不会触发；如果要做公网多用户，才需要认真压测。
- **吞吐目标要先定义**。例如“一份 20 页 PDF 在 2 分钟内处理完”比“每秒多少请求”更贴近真实体验。
- **测量环境要固定**：同一台机器、同一份样本、同一个数据库版本；否则前后数据不可比。
- **先测量再优化，先优化再迁移**。很多“Python 慢”其实是 N+1 查询、缺索引、同步阻塞 I/O 或 Worker 太少。

### 建议的测量基线

1. 选 10–20 份代表性资料（Word、PDF、网页、截图），记录处理耗时、内存和失败原因；
2. 用 k6 或 Locust 对核心接口做一轮基线压测，记录 p50/p95/p99、错误率和吞吐；
3. 打开 `pg_stat_statements`，记录最耗时的 10 条 SQL；
4. 用 `docker stats` 记录 API 和 Worker 的空闲/峰值内存；
5. 记录一次全新安装的耗时、镜像大小和冷启动时间；
6. 每个学期复盘一次，只有连续触发阈值才进入迁移评估。

## 三条候选路径

### 路径 A：不迁移，只替换热点（推荐默认）

**做法**：保持 Python 技术栈，先做低风险优化：

- 升级 Python 小版本（项目当前锁定 3.12；新版本通常有性能改进，但要先跑全量测试）；
- 优化 SQL、补索引、消除 N+1 查询、调整连接池；
- 对重复读取加缓存；
- 增加 Worker 数量、拆分长作业、设置超时和重试；
- 把 CPU 密集的局部逻辑做成独立进程或 Rust 扩展，而不是重写整个后端；
- 用更合适的存储/检索参数（例如 pgvector 索引）解决检索瓶颈。

**优点**：风险最低，不动 API 契约和数据库历史；1–4 周通常能看到效果。
**限制**：如果瓶颈是 Python 解释器本身或必须单文件部署，优化空间有限。
**适用**：绝大多数“感觉慢”的场景。

### 路径 B：分批迁移/绞杀者模式

**做法**：保持 `/api/v1` 契约不变，只把一个边界清楚的上下文换成新服务。例如：

- 只把资料解析 Worker 换成 Go/Rust；
- 只把检索/向量查询换成独立服务；
- 只把高并发只读接口换成 Go 服务。

新旧服务通过 HTTP 或消息队列协作；数据库可以先共用，也可以按需拆库。上线时用双跑、影子读、特性开关和灰度，确认结果一致后再切流量。

**优点**：风险可控，能针对真实瓶颈；其他模块继续用 Python，保留 AI/解析生态优势。
**限制**：一个上下文约 2–4 个月（含契约测试、双跑、回滚和运维）；需要额外部署单元和监控；跨服务事务会更复杂。
**适用**：某个指标连续触发阈值，且路径 A 已无法解决。

### 路径 C：整体重写

**做法**：用另一门语言重写 API、Worker、数据访问和迁移。

**优点**：理论上可以得到统一的性能、部署和类型安全。
**限制**：6–12 个月以上；要重建数据库迁移历史、核对留痕、引用可追溯性、幂等和事务语义；期间新功能基本停摆；团队需要同时维护新旧两套系统。风险远大于收益。
**适用**：只有在“Python 无法满足硬约束，且路径 B 也失败”时才讨论。

### 语言候选对比

| 语言 | 部署 | 并发/性能 | 生态匹配 | 团队学习成本 | 适合场景 |
| --- | --- | --- | --- | --- | --- |
| Python（现状） | 需要解释器和依赖 | 同步 I/O 需靠多进程/异步；CPU 密集受限 | AI、PDF、OCR、网页解析生态最好 | 已掌握 | 业务规则、资料处理、模型编排 |
| Go | 单二进制，部署简单 | 并发好，内存占用低 | Web/队列/网络服务成熟；PDF/OCR/AI 生态较弱 | 2–4 周 | 高并发 API、队列消费者 |
| Rust | 单二进制，性能高 | 性能最好，内存安全 | 系统级/CPU 密集强；开发速度慢 | 1–3 个月 | 解析热点、向量计算、边缘部署 |
| Node/TypeScript | 需要 Node 运行时 | I/O 并发好；CPU 密集较弱 | 与前端同语言；AI/PDF 生态一般 | 2–4 周 | 以 I/O 为主的服务 |
| Java/Kotlin | 需要 JVM，镜像较大 | 成熟稳定，吞吐高 | 企业生态强；与当前团队技术栈距离远 | 1–2 个月 | 大型多用户后端 |

**对本项目而言，Python 在 AI、PDF、OCR、网页解析上的生态优势很难替代。** 如果将来迁移，优先考虑“Go/Rust 只做热点”，而不是把整个后端换掉。

## 迁移必须保持的约束

无论走哪条路径，下面这些不能变：

1. **`/api/v1` 契约**：路径、请求/响应字段、状态码和中文错误原因要兼容；前端不能因为后端换语言而重写。
2. **领域规则与状态语义**：
   - 核对状态 `pending/confirmed/ignored/superseded` 的转换规则；
   - 来源冲突 `source_conflict` 的判定；
   - 版本关系 `same_source` / `replacement_claim`，以及“记录声明不等于接受替代”；
   - 字段差异中“缺失”与“明确删除”的区分；
   - 适用范围“缺失不是通配”的规则；
   - 生效值叠加修正的语义。
3. **数据库迁移历史**：Alembic 迁移和已推送的历史不能重写；新服务必须能读旧数据，变更用 expand/contract（先加新结构、双写/回填、再删旧结构）。
4. **可追溯性**：候选字段、原文证据、字段修正、核对变更、来源片段与定位、版本快照都要保留，不能因为换语言丢失。
5. **工作空间隔离**：跨空间访问一律 404，不泄露对象是否存在。
6. **只读与事务语义**：只读接口不写库、不提交事务；幂等操作重复调用结果一致；事务边界和失败回滚不变。
7. **运维能力**：日志、诊断、备份恢复、健康检查、迁移回滚都要有对应实现。
8. **可回滚**：新服务上线要能切回旧实现；不能出现“切过去就回不来”。

## 建议

1. **现在不立项迁移**，也不做整体重写。当前没有数据支撑，迁移会消耗大量时间并打断 MVP。
2. **先建立测量基线**：按上一节的 6 个步骤，至少收集一个学期的真实使用数据。
3. **优先做低风险优化**：Python 小版本升级、SQL/索引、缓存、Worker 扩容、异步 I/O；这些通常比换语言便宜得多。
4. **触发后再局部替换**：只有某个指标连续触发阈值、且路径 A 无效时，才对那一个上下文走路径 B。
5. **整体重写保持“不建议”**：除非出现明确硬约束（例如必须单文件、无 Python 运行时、极端资源受限），且路径 B 也失败。
6. **前置条件**：
   - 有可重复的压测环境和代表性样本；
   - 有契约测试和结果对照机制；
   - 至少两名成员能维护新旧两套实现；
   - 有回滚、监控和双跑计划；
   - 明确迁移期间新功能是否暂停。

## 明确不做

- 本项不写迁移代码，不改技术栈，不新增服务。
- 不产生“Python 一定慢/一定要换”的结论；当前没有性能数据。
- 不重写 Alembic 迁移历史，不改变 `/api/v1` 契约。
- 不把 F006 当作重构立项；是否迁移由后续实测数据决定。
